## 4. 기존 Harness 확장 설계

### 4.1 리포트 유형

계획 문서에 `report_type: stock_report | ai_scorecard`를 추가한다.

- 필드가 없는 기존 문서는 `stock_report`로 처리한다.
- 알 수 없는 유형, 단계별 문서의 유형 또는 실행 ID 불일치는 차단한다.
- 기존 stock 모드의 단일 ticker 계약은 유지하고, scorecard 모드는 기업 목록을 사용한다.
- 기존 CLI와 일반 리포트 산출물 계약은 유지한다. 채점 모드를 추가하기 위해 기존 요구를 전역으로 완화하지 않는다.

### 4.2 재사용과 분리

| 기존 요소 | 활용 방식 |
|---|---|
| `/stock-goal`과 stock 단계 | 동작 유지. `/score-goal`과 채점 전용 단계 추가 |
| `plan/`, `research/`, `drafts/`, `reviews/`, `output/` | 동일한 체계 사용. 고유 실행 ID로 자료를 분리 |
| `report_contract_lib.py` | 경로, 공통 메타데이터, 출처 및 문서 처리 재사용 |
| `validate_report_contract.py` | 유형별 검증으로 분기. 기존 stock 검증 보존 |
| `build_report.py` | 유형별 렌더러 연결. 기존 빌드 명령 유지 |
| 기존 검토 에이전트 및 메모리 | 채점용 검토 항목, 결과 파일과 운영 기록 추가 |
| `server.js` | 기존 output 미리보기 제공에 재사용 |

- 일반 리포트의 뉴스 수집, 이미지 생성, 기존 디자인 요구는 stock 모드에 유지한다.
- scorecard에는 이미지 생성이나 뉴스 개수 요건을 강제하지 않는다.
- scorecard HTML은 현재의 순위표, 기업별 불릿, 원자료, 차트 중심으로 생성하며 단일 파일로 열 수 있어야 한다.
- 기존 stock 빌드의 가격 재수집과 달리, scorecard 빌드는 검토받은 자료만 사용한다. 최종 생성 중 새 가격을 받아 결과를 바꾸지 않는다.
- 새로운 구조화 파일은 엄격한 파서로 읽는다. 잘못된 형식을 임의의 문자열 해석으로 통과시키지 않는다.

### 4.3 훅과 실행기

- 단계 순서, 필수 자료, 리뷰 상태를 검사하는 공통 Python 검증기를 실행기와 빌더에서 직접 호출한다.
- 훅은 같은 검증기를 호출하는 추가 방어 장치다. 특정 실행 환경의 훅 지원 여부에 핵심 통제를 의존시키지 않는다.
- 기존 훅의 전체 drafts 검색을 실행 대상 중심으로 분리한다. 다른 보고서의 미완성 초안이 현재 실행을 막지 않게 한다.
- stock의 기존 완료 조건은 유지한다. scorecard에는 정상적인 사용자 확인 대기와 정성 판단 대기를 허용한다.
- 계산 결과의 근거는 산식과 원자료 출처로 추적한다. 계산된 점수에 가짜 외부 인용을 붙이지 않는다.
- Windows에서는 설치된 Python 실행 파일을 확인한다. `python3` 명령이나 Bash 훅이 있다는 가정 없이 공통 검사를 실행할 수 있게 한다.

## 5. 규칙 정비와 계산 정책

아래는 구현할 개정안의 방향이다. 현재 운영 규칙을 즉시 대체하지 않는다. 먼저 규칙 변경표와 전 기업 영향표를 제시하여 사용자 승인을 받는다.

### 5.1 규칙 원본과 버전

- 정의, 수치 구간, 체크리스트 ID, 적용 범위를 버전이 고정된 구조화 규칙 원본으로 관리한다.
- 사람이 읽는 규칙 MD는 이 원본에서 생성한다. 숫자 구간과 체크리스트를 여러 문서에 수작업으로 복제하지 않는다.
- 각 실행은 규칙 버전과 해시를 고정한다. 규칙 파일이 바뀌었다고 진행 중 실행이 자동으로 새 규칙을 사용하면 안 된다.
- 규칙 변경은 승인 후 새 메이저 버전으로 관리한다. 이번 정비안의 예정 버전은 v2.0이며 승인 전 활성화하지 않는다.
- 보고서 버전, 규칙 버전, 실행 ID를 구분한다. 같은 날 재생성은 중복 이력을 만들지 않는다.
- 규칙 변경 전후의 점수는 단순 실적 추세로 연결하지 않는다. 필요한 소급 비교는 별도 재평가 기록으로 만든다.

### 5.2 ⑥ 상장사 가격

- 한 실행에서 가격 기준 시점을 고정한다. 휴장일이면 해당 시장의 직전 거래일 종가와 실제 날짜를 기록한다.
- NTM EPS는 기준일 현재 다음 4개 미발표 회계분기의 EPS 컨센서스 합계로 계산한다.
- 주가, EPS의 통화, 보통주/ADR 기준, 분할 조정, GAAP/조정 기준을 확인한다. 기준이 다른 EPS를 섞지 않는다.
- 회계 기준이 확인되지 않거나 4개 분기를 확보하지 못한 경우 자동 채점을 보류한다.
- 연간 EPS를 가중하여 만든 근사치는 정확한 NTM과 구분하여 참고로만 표시한다.
- EPS 합계가 0 이하이면 낮은 PER이나 0점으로 취급하지 않는다.
- 내부 원값으로 판정하고 표시에만 반올림한다.

| NTM PER | ⑥ 점수 |
|---|---|
| 20 미만 | 0 |
| 20 이상, 29 미만 | -1 |
| 29 이상, 42 미만 | -2 |
| 42 이상, 62 미만 | -3 |
| 62 이상, 90 미만 | -4 |
| 90 이상 | -5 |

- 가장 가까운 경계의 ±3%는 주의 표시만 한다. 구간 결과를 다른 지표나 판단으로 덮어쓰지 않는다.
- TTM PER, P/S는 설명과 교차검증에 남기되 상장사 ⑥ 점수의 대체 입력으로 쓰지 않는다.
- 기존 표와 트리거에 다른 경계가 남아 있는지 검사한다.

### 5.3 ⑥ 비상장사와 상장 전환

- 확인된 기업가치와 그 거래 날짜, ARR, TTM 매출, 공개된 이익률을 구분하여 저장한다.
- 기업가치/ARR, 기업가치/TTM 매출을 계산하되 기간이 다른 지표를 같은 종류처럼 표시하지 않는다.
- 점수는 사람이 입력하고 원자료, 선택 사유, 보정 사유와 검토자를 남긴다. 자료가 부족하면 검토 대기다.
- 상장 후에는 상장사 ⑥ 계약으로 전환한다. 상장 직후 컨센서스가 없다는 이유로 비상장 예외를 연장하지 않는다.
- 구주 거래, 신주 조달, 루머를 구분하고 우선주 조건과 시점 차이도 근거에 기록한다.

### 5.4 ⑨ 적자 깊이

- 영업손익과 FCF의 기본 기간은 TTM으로 통일한다. 분기 자료는 추세 판단 근거로 분리한다.
- 표준 FCF는 영업현금흐름에서 현금 설비투자를 차감한다. 회사 조정 FCF는 별도 지표로 보관한다.
- 공시 누적 수치와 개별 분기를 구분하고 중복 합산하지 않는다.
- 현금 소진을 버틸 기간은 TTM FCF가 음수인 경우에만 계산한다.
- 분자는 사용 가능한 현금 및 현금성자산과 조건이 확인된 확정 미인출 여신이다. 제한된 현금, 이미 인출되어 현금에 들어간 여신, 예상 조달은 중복하거나 포함하지 않는다.
- 분모는 TTM FCF의 연간 현금 소진액이다. 3년 이상, 1년 이상 3년 미만, 1년 미만의 경계를 명확히 한다.
- 기존 4단계 판정의 순서, 점수 상하한, 영업손실률 경계, 방향 완화, FCF 0의 처리는 규칙 승인 단계에서 명문화하여 테스트 표로 고정한다.
- 추세 안정/악화, BEP 후퇴, 일회성 항목과 약정 성격은 사람의 검토 입력이다. 계산기가 이를 추측하지 않는다.
- RPO/백로그와 약정은 기간, 범위, 성격이 맞는 경우에만 비교한다. 매출 계약을 현금이나 이익으로 간주하지 않으며 ARR을 계약된 유입으로 대체하지 않는다.
- 이미 FCF에 반영된 지출과 우발 보증을 현금 소진에 다시 더하지 않는다.
- 수집 장애, 실제 미공시, 출처 충돌을 다른 상태로 관리한다. 불확실성의 점수 처리는 승인된 규칙이나 검토 결과로만 결정한다.

- 실적은 기업 공시와 IR을 우선한다. SEC 구조화 데이터로 부족한 항목은 원문 공시와 기업별 공시 체계로 확인한다.
- 가격과 분기 컨센서스는 FMP를 첫 후보로 검증한다. 대상 기업의 실제 커버리지, 회계 기준, 분기 제공 범위, API 요금제와 공유 권한을 확인한 뒤 연결한다.
- 유료 권한이 없어도 출처가 첨부된 수동 입력을 동일한 데이터 계약으로 받아 계산과 검증을 진행할 수 있게 한다.
- 수집 실패 시 다른 기간이나 다른 종류의 지표로 조용히 대체하지 않는다.
- API 키와 비공개 원문은 공유 HTML이나 공개 output에 포함하지 않는다.

### 최소 데이터 계약

- 기업: 안정적인 기업 ID, 표시명, 상장 상태, 종목 및 거래소, 발행사, ADR 비율.
- 원자료: 지표명, 값, 단위/통화, 기간 시작/종료, 공시일, 수집일, 실적/전망 구분, 회계 및 주식 기준, 출처 ID.
- 계산: 입력 원자료 ID, 산식/방법, 계산 결과, 적용 규칙 ID, 경고.
- 판단: factor ID, 점수, 근거 불릿 배열, 검토일, 검토자, 변경/승계 상태.
- 실행: 실행 ID, 기준 시점, 규칙 버전/해시, 자료/판단 해시, 검증 및 승인 상태.

이 원본에서 HTML의 D, VAL, EARN, HIST, TRIG와 MD, CSV를 생성한다. D는 생성된 결과이며 사람이 수정하는 별도 진실로 남기지 않는다.

- 과점/함정/조정 총점, 순위, KPI와 차트는 계산 결과에서 생성한다.
- 정성 점수 승계는 새로 검증되었다는 뜻이 아니다. 마지막 검토일과 이번 실행 검토 여부를 따로 표시한다.
- 원본과 기존 문서가 충돌하면 가져오기 오류로 보고한다. 예전 값의 정정은 별도 변경안으로 처리한다.
- 한국어 근거는 불릿으로 렌더링한다. 통화는 $M/$B/$T, 실적 비교는 상회/하회 표기를 유지한다.
- 채점표에 규칙 요약을 다시 복제하지 않는다. 규칙은 전용 문서로 연결한다.

## 7. 검토와 승인 계약

```text
plan -> research -> calculate -> draft/preview -> review
     -> awaiting_user -> build/finalize
```

- 필수 판단이 없으면 needs_judgment, 자료나 검증 문제가 해결되지 않으면 blocked로 기록한다.
- 네 검토 영역은 사실/출처, 재무 계산, 규칙 일관성, 출력/가독성이다.
- 가능한 경우 독립 검토 에이전트로 수행하고, 영역별 결과 파일과 실행 기록을 남긴다. 수행하지 못한 검토를 수행한 것으로 표시하지 않는다.
- 필수 체크리스트는 항목별 pass/fail/not_applicable과 근거를 남긴다. not_applicable도 사유가 필요하다.
- 기계 검사는 누락과 산술을 검증한다. 이중 계상 같은 의미 판단까지 자동 검증했다고 주장하지 않는다.
- 사용자에게 기존/제안 factor 점수, 합계와 순위 영향, 변경 유형(실적/규칙/정정/경계통과), 출처 및 미해결 항목을 보여준다.
- 사용자 승인은 검토받은 자료, 규칙, 판단의 해시에 연결한다. 하나라도 바뀌면 승인과 관련 리뷰를 무효화한다.
- 최종 빌드는 같은 입력에서 같은 결과를 만들어야 한다. 생성 시각을 점수 근거로 사용하지 않는다.
- 확정 파일을 모두 검증한 뒤 최신 결과를 갱신한다. 중간 실패로 MD/HTML/CSV의 최신 버전이 갈라지지 않게 한다.
- 같은 승인본 재실행은 CSV나 운영이력에 중복 행을 만들지 않는다.
- 최종 사용자 보고는 바뀐 점수, 이유, 순위 영향 중심으로 간결하게 한다.

## 8. Orca 작업 분할

아래 작업 ID는 인계용이다. Orca의 특정 API나 설정 문법을 가정하지 않는다.

| ID | 작업 | 선행 조건 | 산출물 | 통과 조건 |
|---|---|---|---|---|
| P0 | 원본/저장소 조사와 기준선 보존 | 없음 | 시작 커밋, 파일 해시, 기업 목록, 기존 검사 결과, 충돌 목록 | 자료 위치와 기존 불일치가 기록됨 |
| P1 | 규칙 개정안 정비 | P0 | 규칙 변경표, 구조화 초안, 경계 테스트 표, 전 기업 영향표 | 사용자가 규칙을 승인 |
| P2 | 유형별 계약과 공통 검증 기반 | P1 | stock/scorecard 분기, 데이터 계약, 실패 상태, 기존 모드 테스트 | 기존 명령/요건 보존, 잘못된 유형 차단 |
| P3 | 재무 입력과 계산 | P2 | 수동 입력, 데이터 어댑터, ⑥⑨ 계산기, 계산 테스트 | 승인 규칙과 계산 결과 일치 |
| P4 | 기준선 가져오기와 출력 생성 | P2 | 원본 이관 보고, MD/HTML/CSV/이력 생성기, 미리보기 | 승인 없는 점수 변경 없음, 출력 간 일치 |
| P5 | 실행 흐름과 검토/승인 연결 | P3, P4 | score-goal, 리뷰 결과 계약, 승인 결합, 훅 연결 | 검토 누락/오래된 승인으로 확정 불가 |
| P6 | 통합 회귀 및 시각 검증 | P5 | 두 모드 테스트 결과, 실패 사례 결과, 화면 검증 | 기존 기능 회귀 없음, 채점 일관성 통과 |
| P7 | 첫 변경안 확인과 전환 | P6 | 사용자 변경안, 승인된 보고서 및 이력 | 별도 사용자 승인 후에만 확정 |

### 병렬 실행과 소유권

- P0/P1은 원본과 규칙을 확정하는 선행 작업이다. 여기서 발견한 모순을 다른 에이전트가 임의로 보정하지 않는다.
- P2 이후 P3와 P4만 병렬로 진행한다. P3는 입력/계산, P4는 가져오기/렌더링을 소유한다.
- 공통 데이터 계약, 타입 분기, 검증 진입점과 훅은 통합 담당자 한 명이 소유한다.
- 공통 계약 변경이 필요하면 먼저 통합 담당자에게 변경안을 전달하고 계약을 갱신한 뒤 양쪽에 반영한다.
- 검토 담당은 구현 결과를 읽고 문제를 반환한다. 다른 담당의 파일을 직접 덮어쓰지 않는다.
- 각 단계는 변경 파일, 수행 검사, 미해결 사항, 다음 단계 입력을 짧은 작업 결과로 남긴다.
- 사용자 승인 대기 중인 단계를 완료 처리하거나 다음 승인 단계를 자동으로 통과시키지 않는다.

## 9. 필수 검증 시나리오

### 일반 리포트 회귀

- report_type이 없는 기존 문서와 명령이 계속 동작한다.
- stock 모드의 이미지, 뉴스, 리뷰, 출력 계약을 계속 강제한다.
- scorecard에만 추가한 대기 상태나 이미지 면제가 stock 모드에 적용되지 않는다.
- 외부 데이터를 고정한 fixture로 기존 렌더링과 검증을 비교한다.

### 계산 및 자료

- PER 20/29/42/62/90의 직전/정확한 경계/직후, 표시 반올림과 내부 판정 차이.
- EPS 누락/0/음수, 회계연도 차이, 4분기 부족, ADR/통화/분할/회계 기준 불일치.
- 누적 현금흐름과 분기 현금흐름 중복, FCF 부호, 제한 현금과 여신 중복.
- 현금 소진 기간 1년/3년 경계, 약정 기간 불일치, ARR의 계약 유입 대체 차단.
- 자동 계산이 끝났어도 필요한 정성 판단이 없으면 확정하지 않음.

### 운영 및 출력

- 체크리스트 누락, 근거 없는 not_applicable, 미수행 리뷰, 승인 후 자료/규칙/판단 변경.
- 정상 사용자 대기, 서로 다른 실행 간 간섭, 동일 승인본 반복 확정, 확정 중 실패.
- 기존 14개사 가져오기 전후 점수 보존. 기존 MD/HTML/CSV 불일치를 숨기지 않음.
- MD/HTML/CSV의 점수, 합계, 순위, 원자료, 이력 일치.
- 기존 check_채점표.py의 유효 검사를 재사용/확장하고 하드코딩된 버전 의존 제거.
- HTML 인라인 JS 문법과 데스크톱/모바일 Playwright 화면 검증. 표 잘림, 불릿, 산점도 겹침, 빈 차트 확인.
- 공유 HTML의 민감 자료/API 키 제외 및 데이터 재배포 권한 확인.

## 10. 완료 정의와 첫 실행 지시

### 첫 버전 완료 조건

- 기존 일반 리포트가 계속 동작한다.
- 승인된 규칙 버전으로 전체 기업에 동일한 계산과 필수 검사를 적용한다.
- 누락 자료와 사람이 판단할 부분을 명확히 드러낸다.
- 사용자 승인 전 점수와 최종 이력을 바꾸지 않는다.
- 동일 실행 원본에서 생성된 모든 결과가 일치한다.
- 기존 v1.5 기준선과 원문은 보존한다. 전환 후 활성 원본 위치를 안내 문서에 명시하여 이중 편집을 방지한다.

### Orca에 전달할 시작 지시

> stock-report-harness의 기존 일반 종목 리포트를 유지하면서 AI 기업 채점 모드를 추가한다. 이 문서를 기준으로 먼저 P0와 P1을 수행하라. 실제 원본과 현재 저장소를 읽고, 기준선 검사 결과와 규칙 충돌 목록, 개정안 및 전 기업 영향표를 제시하라. 사용자 승인 전 규칙을 활성화하거나 기존 점수를 수정하지 말라. 승인 후 P2를 진행하고 계약을 고정한 다음 P3/P4를 병렬화하라. 유료 가입, 원격 반영, 공개 배포는 별도 승인 없이 수행하지 말라.
