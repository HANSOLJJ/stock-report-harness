
## F9-DECIDE-20/20B — 독립 시뮬레이터의 한계

C-13 과 NTM 이 각자 독립 시뮬레이터를 짜서 F9 미결 5건의 영향을 실측했다.
**둘 다 핵심 결론이 틀렸고, 서로 반대로 틀려서 2자 대조로 드러났다.**

- C-13 — C-16 이 alibaba 를 −2/−3 으로 가른다 → 입력이 둘 필요한데 하나만 적음
- NTM — C-16 downgrade 가 amazon 을 −3 으로 푼다 → amazon 은 두 관문에 막혀 안 풀림

출하 엔진 `calc_f9.py` 를 직접 불러 16개 조합을 돌리니 **실제로 움직이는 것은
C-06 + C-05 diagnose_only 가 spacex-xai 를 −4 로 푸는 하나뿐**이고 C-16 은 0개사다.

**배운 것.** F6-SPEC-18 에서 "두 쪽이 같은 전제를 쓰면 일치가 정답을 뜻하지 않는다"
를 배웠는데, 이번은 **서로 다른 전제를 써서 서로 다르게 틀린** 경우다.
독립 시뮬레이터는 규칙 해석을 검증하지만 **구현과의 일치는 검증하지 않는다.**
→ 규칙 영향 조사의 완료 조건에 "출하 엔진 호출 대조" 를 넣는다.

**내 전제도 틀렸다.** 지시서에 F9 None 기업을 3개라고 썼는데 4개였고
빠진 spacex-xai 가 유일하게 풀리는 기업이었다. NTM 이 실측으로 정정했다.

**구조적 발견.** F9 를 막는 것은 규칙 공백이 아니라 입력 부재다.
`coverage_comparable` 11/14 unknown(관측 0건) · `revenue_ttm` 0/14 ·
`operating_income_ttm` 0/14. 10개사가 G1 을 수치 없이 검토된 부호로 통과한다.
F6 수집이 뒤의 둘을 채운다 — factor 간 의존이 여기서 드러났다.

## 상태 라벨이 판정을 가르면 라벨의 뜻부터 확인한다

사용자가 **"일단 그 데이터가 없는 게 맞아?"** 라고 물어 원자료를 열었다.

```
spacex-xai.offbalance_B   status = not_disclosed   raw = "미확인"
```

**status 와 raw 가 서로 다른 사실을 말하고 있었다.** 전수로 보니 `not_disclosed`
하나에 네 뜻이 섞여 있다 — 미확인 / 미공시 / 계산 대상 아님 / 없음.

`calc_f9._g4()` 가 `status == "not_disclosed"` 로 C-16 진입을 가르므로,
**우리가 안 찾은 것이 그 기업의 미공시 위험으로 둔갑한다.** 설계 지침 6.4 가
금지하는 바로 그 일이고, 코드는 지침을 구현했는데 입력이 구현을 배신했다.

**놓칠 뻔했다.** C-13 이 amazon 에서 `parse_failed` 를 잡아낸 덕에 구분의 존재는
알고 있었는데, **같은 구분이 다른 기업에서 깨져 있는지는 안 봤다.** 한 기업에서
발견한 결함은 전수로 확인해야 한다.

**결정 순서가 바뀌었다.** C-16 을 정하기 전에 `offbalance_B` 를 실제로 찾는다.
찾아지면 C-16 이 필요 없어지고, 확인했는데 없으면 그때 비로소 C-16 이 묻는
상황이 된다. **지금 정하면 찾아보지도 않고 감점하거나 봐주는 것이다.**
