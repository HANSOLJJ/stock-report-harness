## Entry: 2026-10-01 — 채점 실행 리뷰가 세 바퀴 돌았다
- **상황**: 시험 실행 `ai-scorecard-2026-10-test` 의 4영역 리뷰. 조율자(Claude)가 리뷰어 넷을 서브에이전트로 띄우고, 발견을 판단 변경 제안(PRP-001~007)으로 올려 사용자가 승인 페이지에서 반영했다.
- **증상**: 리뷰 → 제안 반영 → 재리뷰 → 또 제안이 세 번 돌았다. 판단이 바뀔 때마다 판단 해시가 바뀌어 research → calculate → draft → review 를 다시 밟았고, 사용자는 매번 제안을 다시 눌렀다. 사용자 원문: "이게 이 리뷰로 한번에 다 잡아내는게 맞지 않아? 이거 무한반복이자나", "한방에 가야해".
- **원인**: 셋이다. (1) 조율자가 1차 리뷰 지시서에 "바뀐 것 위주·표본 대조로 충분" 이라고 범위를 좁혀, 이어받은 판단 문장의 옛 숫자(Oracle ⑨ 영업이익·마진, 아마존 ⑨ 순부채)를 1차에서 아무도 전수로 보지 않았다. (2) 조율자가 고치면서 새 결함을 만들었다. PRP-002 문장에 옛 런웨이 10.6년을 옮겼고, 이해상충 기준을 좁게 잡아 NVIDIA·SpaceX(xAI)를 빠뜨렸다. (3) 숫자 대조·이해상충·트리거 출처·근거 ID 연결처럼 기계로 전수 확인할 수 있는 것을 리뷰어 눈에 맡겼다.
- **해결**: 3차부터 needs_fix 기준을 "점수·순위·체크리스트 판정을 바꾸는 것" 으로 좁히고, 나머지 low 는 각 `review-parts/<영역>.md` 의 "다음 실행 과제" 절로 넘겼다. 다음 실행부터 지킬 순서는 이렇다. ① 리뷰 전에 기계 점검(판단 문장 숫자 ↔ verified 관측, 출처 이해상충, 트리거 출처 등록, 초안 근거 ID 연결)을 돌려 조율자가 먼저 고친다. ② 리뷰 지시서는 표본 대조를 금지하고 이어받은 판단까지 전수로 보게 하며 발견을 한 번에 다 적게 한다. ③ 사람에게 올릴 제안은 리뷰가 끝난 뒤 한 묶음으로 올리고, 고친 문장의 숫자는 올리기 전에 관측과 대조한다.
- **검증**: 3차 확인에서 네 영역 모두 pass(results_hash d82fcfa1…, draft_hash 30135ffb…). 리뷰 전 기계 점검 스크립트는 아직 없다(TODO). 미검증.

## Entry: 2026-10-01 — 리뷰어가 SEC User-Agent 에 사용자 이메일을 넣었다
- **상황**: 같은 시험 실행의 사실·출처 리뷰. 리뷰어 서브에이전트가 공시 원문을 확인하려고 SEC EDGAR 를 직접 조회했다.
- **증상**: 요청 User-Agent 에 환경의 `SEC_UA` 대신 세션 컨텍스트에 있던 사용자 이메일을 넣었다.
- **원인**: `collect` 는 공시 목록만 저장하고 본문(10-Q 등)은 저장하지 않는다. 리뷰어가 원문을 대조하려면 SEC 에 직접 요청해야 했는데, `SEC_UA` 를 쓰는 정해진 도구가 없어 요청을 손으로 만들다 손에 닿는 값을 골랐다.
- **해결**: 2026-10-02 `scorecard_cli.py sec-get <SEC 주소>` 를 만들었다. 코드가 `SEC_UA` 로 요청하고 `data/_sec/docs/` 에 저장하며 같은 주소는 다시 요청하지 않는다. `fact-checker` 와 `score-review` 스킬에 "SEC 원문은 sec-get 으로만, 요청·User-Agent 를 직접 만들지 않는다" 를 넣었다.
- **검증**: `tests/test_sec_get.py` 4건(SEC_UA 로 요청, 캐시 재사용, SEC 주소만 허용, SEC_UA 없으면 요청 전 중단) 통과. 2026-10-01 3차 리뷰어는 SEC 요청을 하지 않았는데, 이는 사고가 재발하지 않았다는 뜻일 뿐 원문 대조를 한 것은 아니다(검증된 관측값과만 대조했다).
