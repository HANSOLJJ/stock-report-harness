# 실적 반영 실행 — 결정 기록

계획 파일과 체크리스트는 결정이 다 모인 뒤에 쓴다. 이 파일은 대화에서 정한 것을 정한 순서대로 남긴다.

## 배경 (2026-10-21)

- Alphabet·SpaceX-xAI 3분기 실적이 나왔다. 지금 구조에서는 실적 하나를 반영하려 해도 정기 실행이 되어 14개사 정성 판단 191건을 전부 다시 매기고 4영역 리뷰를 실행 전체로 한다(`rules.md` 2.9, `validate.rejudge_findings`). 사용자가 "실적 발표마다 전부 다시 돌리는 것은 너무 무겁다"고 했다.
- 실행 종류는 정기 실행과 기업 추가 실행 둘뿐이고, 구분은 `run.json` 의 `continued_from.added_companies` 하나로 한다(`validate.py` 274~277).
- 기존 기업이 움직이지 않았음을 증명하는 `diff` 는 v3.0 실행에서 `SchemaError` 로 멈춘다(`compare.py` 189~193).
- 회사만 골라 수집하는 길은 이미 있다(`collect --company`). 트리거 136건 중 실적 관련이 40여 건이다(v30full).

## 결정

### D1. 실적 반영 실행을 새 실행 종류로 만든다 (2026-10-22)

- 선택지: A 실적 반영 실행, B 시즌마다 정기 실행 한 번, C A + 분기 정기 실행. 사용자가 A 를 골랐다.
- 상장사는 자기 실적이 나올 때마다 다시 매겨지므로 판단이 한 분기를 넘겨 묵지 않는다. 2.9절의 취지(승계 판단이 재검토 없이 이어지는 것을 막는다)는 이것으로 대부분 지켜진다. 분기 실적이 없는 비상장사(Anthropic·OpenAI)의 신선도는 따로 정한다(D4 예정).

### D2. 가격은 모든 회사를 새로 받는다 (2026-10-22)

- 선택지: ㄱ 갱신하는 회사만 새 가격, ㄴ 모든 회사 새 가격. 사용자가 ㄴ 을 골랐다.
- 근거: 오늘 가격 ÷ 가장 최근 공시 재무가 PER 의 원래 정의라서, 실적을 아직 내지 않은 회사에 새 가격을 써도 어긋나지 않는다. 리포트 전체가 한 가격 날짜를 쓰고, 실적 시즌의 주가 변동이 ⑥ 에 곧바로 반영된다. 가격 수집과 ⑥ 계산은 코드가 하므로 일이 거의 늘지 않는다.
- 처음에 ㄱ 을 "회사마다 재무와 가격이 같은 날짜라 앞뒤가 맞다"는 이유로 추천했다가, 사용자 질문으로 다시 따져 보고 철회했다.
- 따르는 일
  - 규칙: 가격 기준일까지 실적을 낸 회사는 모두 갱신 범위에 넣는다. 빠지면 "발표 뒤 가격 ÷ 발표 전 재무" 가 되어 정말 어긋난다. 검증기가 확인한다.
  - `diff`: 가격 관측이 바뀌어 생긴 ⑥ 변화(와 그에 따른 합계·순위 변화)는 허용하는 예외를 넣는다.

### D3. 갱신 범위는 자료가 정한다 (2026-10-22)

- 선택지: ㄱ 실적을 낸 회사만, ㄴ 실적을 낸 회사는 전부 + 닿는 회사는 닿은 항목만, ㄷ 닿는 회사도 전부. 사용자가 ㄴ 을 골랐다.
- 실적을 낸 회사: 정성 판단 전부를 다시 매긴다(그 회사에 한해 정기 실행과 같다).
- 닿는 회사: 이번 실행에서 새로 확정한 근거나 발동한 트리거가 가리키는 (회사, 항목)만 다시 매긴다. 다시 매기지 않으면 research 가 막는다. 에이전트 재량이 아니라 근거·트리거 기록이 범위를 정하므로 빠뜨림을 코드로 잡는다.
- 사용자가 이유를 적고 회사를 직접 범위에 넣는 길을 둔다(실적 사이의 합병 같은 큰 사건).
- ㄱ 은 같은 사건을 닿는 모든 회사에 같은 성격으로 읽는다는 2026-10-09 지시(AGENTS.md 「금지·주의」)를 지키지 못해 뺐다. ㄷ 은 실적 하나에 여러 회사를 통째로 다시 매기게 되어 뺐다.

### D4. 판단 나이 상한 120일 (2026-10-22)

- 분기 실적이 없는 회사는 Anthropic·OpenAI 둘이다(`companies.json` 의 `listed: false`). 이 두 회사는 실적 반영 실행이 자기 차례로 오지 않아, 닿은 항목만 가끔 다시 매겨지고 나머지는 계속 이어받을 수 있다.
- 선택지: ㄱ 판단 나이 상한, ㄴ 비상장사는 정해진 날 갱신, ㄷ 비상장사는 사용자 지정 때만. 사용자가 ㄱ 을 골랐다.
- 규칙: 어느 회사든 마지막으로 전부 다시 매긴 날로부터 120일이 지나면, 다음 실적 반영 실행에 그 회사를 반드시 넣는다. 검증기가 막는다. 상장사와 비상장사를 가리지 않고, 실적 공시가 늦어진 상장사도 함께 잡는다.
- 120일인 이유: 상장사도 3분기 실적에서 연간 보고서까지 넉 달 가까이 걸릴 때가 있어 90일이면 정상 상장사가 걸린다.

### D5. 리뷰는 갱신 범위 전수 + 같은 층 경쟁사 비교 + 나머지는 diff (2026-10-22)

- 선택지: ㄱ 실행 전체, ㄴ 갱신 범위 전수 + 경쟁사 잣대 비교 + 나머지 `diff`, ㄷ 갱신 범위만. 사용자가 ㄴ 을 골랐다.
- 영역별
  - 사실·출처: 갱신 범위에서 새로 확정한 근거만 원문과 대조한다.
  - 재무 계산: 갱신 회사의 재무를 보고, 14개사의 새 가격은 기준일·통화·주식 기준만 확인한다.
  - 규칙 일관성: 갱신한 판단을 같은 층 경쟁사의 이어받은 판단과 나란히 놓는다. 새 잣대가 경쟁사에도 닿아야 하면 그 경쟁사 항목을 같은 실행에서 범위에 넣어 다시 매긴다(Q03 원칙). 사건 교차표·미확인 방향표·근거 등급표는 갱신 범위의 사건으로 만든다.
  - 출력·가독성: 갱신 회사의 카드, ⑥·순위가 바뀐 자리, 회사별 반영 날짜 표시.
- 나머지 회사·항목이 움직이지 않았다는 사실은 `diff` 출력으로 갈음하고 사람이 다시 읽지 않는다(기업 추가 실행 축약 리뷰와 같은 원칙).
- ㄱ 은 리뷰가 그대로 무거워 A 의 효과가 절반으로 줄어 뺐다. ㄷ 은 2026-10-09 OpenAI–Anthropic ⑤ 어긋남 같은 경쟁사 간 잣대 차이를 놓쳐 뺐다.

## 구현 선택 (에이전트, 2026-10-22)

### D6. 규칙을 v3.1 로 올린다

- 실적 반영 실행은 2.9절에 세 번째 실행 종류를 더하는 규칙 변경이고, 나이 상한 같은 값은 규칙 JSON 의 `policies.rejudge` 에 둔다.
- v3.0.json 을 고치면 그 해시가 묶인 v30full 확인 기록이 무효가 된다(`approval_mismatches` 의 rules). 그래서 v3.1.json 을 새로 만들고 점수 규칙은 v3.0 과 똑같이 둔다. 코드에 v3.0 을 박은 곳은 테스트뿐이다.

### D7. 추가 항목은 선언하고, 실적 감지는 실행 폴더 안 자료로 한다

- 리뷰가 같은 층 경쟁사 항목을 범위에 넣을 때(D5) 그냥 고치면 `diff` 가 "범위 밖 수정"으로 잡을 수도, 아무 수정이나 허용할 수도 있다. `run.json` `update_scope.extra` 에 (회사, 항목, 이유)를 선언하게 해서, 검증기는 그 항목의 재판단을 요구하고 `diff` 는 그 항목의 수정만 허용한다.
- 실적 감지는 gitignore 된 `data/` 캐시 대신 실행 폴더의 `candidates.json` 을 읽는다. 다른 기계에서 계약 검증을 돌려도 같은 답이 나와야 하기 때문이다. `collect_filings` 가 이미 읽는 `items`(8-K 항목 번호)·`report_period` 를 후보에도 남긴다.
- 6-K 만 내는 TSMC·Alibaba 는 항목 번호가 없어 기계로 실적 공시를 가를 수 없다. research.md 에 기간 안 6-K 목록을 싣고 리뷰가 본다.

### D8. 첫 실적 반영 실행 q3a 의 진행 방식 (2026-10-23)

- 사용자가 Alphabet 을 기다리지 않고 SpaceX·Meta·Tesla·TSMC 넷으로 먼저 돌리기로 했다(10-23). Alphabet 은 EDGAR 에 10-22 까지 공시가 없다. 기존 `q3` 폴더는 훅이 `init --force` 를 막아(명령문의 v30full 이름을 대상으로 읽는다) 새 slug `q3a` 로 만들었다. `q3` 폴더는 untracked 로 남아 있다.
- 공유 파일(observations·evidence·sources·triggers·judgments)에 여러 에이전트가 동시에 쓰면 덮어쓰기가 난다. 그래서 읽기는 병렬, 쓰기는 조율자가 순서대로 한다.
  - 1단계(Sonnet 넷, 병렬): 회사마다 공시 원문을 읽어 스크래치 조각(관측·출처·근거 candidate·트리거 carry·facts.md)을 만든다. 타사 근거는 `EV-<회사>-NEWn`, 새 트리거는 `TRG-NEW-n` 으로 두고 `merge.py` 가 번호를 매긴다(회사 자신의 번호를 먼저 전부 넣고 타사 NEWn 을 그다음에 매겨야 충돌이 없다).
  - 조율자가 합친 뒤 `confirm` 으로 근거 135건을 확정했다(확정으로 Alphabet ⑤⑧·Anthropic ⑤⑦⑧·Apple ⑧·NVIDIA ⑧ 이 범위에 들어왔다. 범위 58건).
  - 2단계(Opus high 다섯, 병렬): 회사마다 `judge_spec.json`(judge --json 모양의 changes 또는 reconfirm 목록)을 쓰고, `apply.py` 가 순서대로 `revise_judgment` 를 부른다.
- 1단계가 남긴 사용자 결정 후보: SpaceX `cash` 정의(현금만 1.40년 vs 단기 시장성 증권 포함 2.38년 런웨이) — 기존 정의 유지, 바꾸려면 규칙 결정. TSMC 3분기 플랫폼별 매출은 공시 금액이 없어 규칙대로 `unknown` 처리를 2단계에 맡겼다.
- 가격: 10-22 종가가 처음 받을 때 없어 10-21 종가로 들어갔고 TSMC·Alibaba ADR 시가총액이 실패했다. 종가가 나오면 `collect --kind prices` 를 다시 돌린다. 같은 출처(SRC-YF-<가격 기준일>)가 있으면 수집이 회사를 통째로 건너뛰므로, 다시 받으려면 그 출처의 관측을 걷어 내야 한다(10-23 한 번 걷어 내고 다시 받았으나 10-22 종가가 여전히 비어 결과가 같았다).

### D10. q3a 리뷰에서 바뀐 것과 사용자에게 올린 결정 (2026-10-23)

### D11. ⑤ 받은 투자 절충안 (2026-10-23 사용자 결정)

- 사용자가 "받은 투자는 지분 동맹이 아니다" 규칙에 반론을 제기했다. 반론의 핵심: 묶임은 돈의 방향과 무관하고(투자자가 주력 편입·조건부 출자로 묶인다), 비상장 모델사는 남에게 출자할 자본이 없어 지분 동맹이 구조적으로 0 이다. 재반론: 투자자는 헤지한다(Microsoft–OpenAI).
- 절충안 채택: 받은 투자는 투자자가 묶였다는 증거(독점·우선 조항, 주력 편입, 이정표 조건부 추가 출자)가 있을 때만 지분 동맹으로 센다. 증거 등급은 공시·회사 1차 발표·등급을 적은 2차 보도(유출 문서 제외). 헤지가 확인되면 해제. ⑦⑧ 감점은 그대로. 관계사(Q18)는 여전히 제외.
- 제외 규칙은 rules.md 문장에만 있었고 규칙 JSON·계산 코드에는 없어 v3.1 해시를 바꾸지 않고 rules.md 만 고쳤다(체크리스트 Q19 "곧바로 셌나" 문구는 그대로 맞는다).
- 헤지 해석(10-23 저녁): 판단 세션이 "투자자가 자체 모델을 쓰거나 경쟁 모델사에 출자했으면 풀림"으로 넓게 읽어 Anthropic ⑤ 가 4 그대로였다. 사용자가 좁은 읽기(투자자가 내 제품을 주력에서 내렸거나 그 자리에 경쟁 모델을 올린 때만)를 골랐다. rules.md 문장을 그 뜻으로 고쳤고, Anthropic 은 Amazon(이정표 조건부 금융 한도)·Google(조건부 추가 출자)이 서서 ⑤ 4 → 7, OpenAI 는 Microsoft 가 GitHub Copilot 에 자체 모델을 '그 자리에' 넣어 좁은 읽기로도 헤지라 ⑤ 6 그대로다.
- q3b 1차 리뷰(10-23 밤): 규칙 일관성·사실 리뷰가 OpenAI ⑤ 의 넓은 읽기 잔재와 TSMC·SpaceX ⑤ 의 옛 규칙 문장을 잡았다. OpenAI ⑤ 는 Microsoft 의 주력 편입("바꾸기 어려움")이 1차 근거로 서지 않아 세지 않고, 최대 파트너 긴장을 Microsoft 쪽과 맞춰 '있음'으로 바꿔 6 → 5. TSMC ⑤ 는 빠져 있던 관계기업 지분(SSMC·GUC·Xintec·VIS, 맺은 출자)을 세어 12 → 15 로 조정총점 35(Amazon 33 을 제치고 3위). 합작법인 원칙은 "내가 지배하면 관계사(소수 지분은 받은 투자), 지배하지 않으면 맺은 출자"로 통일(OpenAI·Oracle 판단과 같음). 다른 회사의 관계기업 지분 누락 여부는 다음 정기 실행 과제.
