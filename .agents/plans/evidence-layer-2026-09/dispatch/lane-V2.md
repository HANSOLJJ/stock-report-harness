## 검토 축 (각 축마다 실제 명령으로 재현한다)

1. **첫 검증 발견의 실제 해소.** 레인 V 보고서의 F-1~F-7 재현 명령을 사본에서 다시 돌려 막히는지. 레인 H 가 남긴 "계약 밖 쓰기 형태" 가 레인 J 이후 실제로 막히는지.
2. **판단 수정 기능의 안전성.** 판단을 고치면 승인이 반드시 무효가 되는가. 점수 칸 직접 수정(F3·F5·F7·F9)이 정말 막히는가. 형식 오류에 아무것도 쓰지 않는가. `revision_history` 가 이전 값을 보존하는가. 다음 실행(`init --from-run`)이 수정된 판단을 출처와 함께 이어받는가. 승인 페이지 POST 의 코드 검사·루프백·인자 생성. 판단 수정이 승인 우회 통로가 되지 않는가(예: 판단을 고쳐도 승인 해시가 그대로인 경로).
3. **승인 첫 방어선.** 에이전트 표지가 있는 프로세스에서 `stages` 의 승인·취소 함수를 직접 부르면 거부되는가. `allow_agent_session` 이 CLI·승인 페이지 어디에서도 노출되지 않는가.
4. **수집기 실측 수정.** NaN 종가 행 건너뛰기와 `close_date`, 회사별 실패가 다른 회사 기록을 막지 않는지, `SEC_UA` 영문 검사가 값 없이 오류를 내는지, `companies.json` 변경 뒤 기존 두 실행의 `results_hash`·`approval_valid` 가 그대로인지. 네트워크는 쓰지 않는다(픽스처·주입 fetch).
5. **로컬 설정 파일 읽기.** 워크트리에서 원본 체크아웃 루트의 설정 파일을 찾는 코드가 엉뚱한 경로를 읽을 수 있는가. 테스트가 사용자의 실제 설정 파일을 읽지 않는가.
6. **원자료 건너뛰기.** 레인 T 의 `require_raw` 가 원자료가 있을 때 실제로 테스트를 실행하는가. 건너뛰기가 원자료와 무관한 실패를 숨기지 않는가.
7. **문서와 코드 일치.** README·AGENTS·structure.md·score-* 스킬의 명령·인자가 `--help` 와 맞는가. 에이전트에게 승인·취소를 시키는 문구가 남았는가.

## 산출물

- 보고서 `validation/lane-V2-recheck/REPORT.md`. 발견마다 심각도(high·medium·low), 위치(`파일:줄`), 재현 명령과 실제 출력, 왜 결함인지, 고치는 방향(한두 문장). 발견이 없는 축은 확인한 명령을 적는다. 마지막에 "main 병합을 막아야 할 발견" 을 따로 모은다. 레인 V 의 F-1~F-7 각각에 대해 "해소 / 일부 / 미해소" 를 표로 적는다.
- 보고서만 한 커밋. `docs(validation): 통합 브랜치 독립 재검증 보고서`.
- 코드·테스트·문서·기존 실행 파일을 고치지 않는다. 임시 파일은 시스템 임시 폴더에 두고 저장소에 남기지 않는다. `git stash` 금지. 승인 명령을 기존 두 실행에 돌리지 않는다. `SEC_UA` 값을 출력하지 않는다. 셸 명령 문자열에 보호 경로·승인 명령이 들어가면 훅이 막는다. 필요하면 페이로드를 파일로 만들어 확인한다.
- 완료는 preamble 의 `worker_done`(발견 수와 병합 차단 여부를 세 문장 요약에) 뒤 조율자 터미널 `term_be1eaaf8-815c-4231-a858-7229d925e5fe` 에 한 줄 안내.
