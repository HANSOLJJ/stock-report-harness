# `nonop_share` — 저장값이 옳고 재계산이 틀렸다

- 검토일. 2026-09-14.
- 발견. 설계진행이 worker 저장소 안의 companyfacts 로 직접 검정.
- 결과. **저장값 = `영업외손익 ÷ 세전이익`. 8/9 재현.**

## 경위

worker 가 `nonop_share` 저장값과 재계산값이 12개사 중 11개에서 갈리고 여섯은 부호가 뒤집히는 것을 등재하며 이렇게 닫았다.

> 저장값에 basis 가 없어 **확인할 수 없다**

**자료가 그 저장소 안에 있었다.** `validation/f6-avail-15/_raw/` 에 companyfacts 12개.

```
가설 B   (NI − OI + tax) / (NI + tax)  →  8/9   (±0.03)   ← 저장값
```

## 엔진 산식이 두 군데 틀렸다

```
현행   (NI − OI) / NI
정정   (NI − OI + tax) / (NI + tax)  =  (세전이익 − 영업이익) / 세전이익
```

1. **분자에 세금이 섞임** — worker 가 찾았다.
2. **분모가 당기순이익** — 세전이익이어야 한다. **이것은 아무도 못 찾았다.**

**저장값이 옳고 재계산이 틀렸다. 오늘까지 반대로 알고 있었다.**

## 점수 영향 — 오늘은 없고 경계 우려가 사라진다

```
amazon   재계산 0.3073  임계 +2.4%    ← 내가 경계로 지적한 값
         정정   0.4571  임계 +52%
alphabet 재계산 0.3955  →  정정 0.5085
뒤집힌 여섯   정정하면 전부 0 근처. hit 여부 안 바뀜
```

**순위 불변.** 그리고 내가 `nonop_share_boundary` 를 붙이라 한 이유가 정정으로 해소된다. **표시는 유지한다** — 다음에 또 경계에 붙는 값이 나온다.

`spacex-xai` 는 NI·OI 둘 다 음수라 **정정해도 부호 규약이 안 선다.** worker 의 `negative_denominator` 경고를 유지한다.

## 방법론 — 같은 방법을 한 자리에만 썼다

**`net_cash` 에서는 후보 정의 다섯을 legacy 값에 대 보고 역산했다. `nonop_share` 에는 그 방법을 안 썼다.**

`basis` 가 없다는 것은 **"저장값이 무엇인지 적혀 있지 않다"** 는 뜻이지 **"무엇인지 알아낼 수 없다"** 는 뜻이 아니다. 값이 12개 있고 후보 산식이 유한하면 맞춰 볼 수 있다.
