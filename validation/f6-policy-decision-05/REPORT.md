작성일 2026-09-09. 담당 worker(HANSOLJJ/worker). 요청 메시지 `msg_8d534db4df12`.

**코드·점수·승인은 변경하지 않았다.** 이 보고서 한 건만 추가한다. **Nasdaq API 는 이번 작업에서 한 번도 호출하지 않았다**(지시 준수).

## 2. 게이트 조사

### 2.1 Nasdaq — 라이선스 경로는 있으나 우리 상품인지 미확인

지시대로 `robots.txt`·약관만으로 제외하지 않고 정식 경로를 조사했다. **추가 API 호출은 하지 않았다.**

| 항목 | 확인 내용 |
|---|---|
| 상업 이용 계약 | **Nasdaq Global Data Agreement**. 데이터 피드를 상업·부가 서비스로 제공할 때 서명이 요구된다 |
| 신청 절차 | **Data Feed Request Form** 제출 → 시스템 설명(System Description) 승인 → 라이선스 부여 |
| 라이선스 성격 | 전 세계·비독점·양도불가. **승인된 용도 범위 안에서만** 수신·사용·처리·저장 허용 |
| 문의 창구 | Nasdaq Global Data Products Administration, `DataOps@nasdaq.com` |
| 별도 경로 | Nasdaq Data Link(구 Quandl) `data.nasdaq.com/terms` — 별도 약관·요금제 |

출처: [Global Data Agreement](https://www.nasdaq.com/docs/globaldataagreement.pdf) · [Data Feed Request Form](https://www.nasdaq.com/docs/datafeedrequest.pdf) · [Nasdaq Data Link 약관](https://data.nasdaq.com/terms) · [Legal | Nasdaq](https://www.nasdaq.com/legal)

**중요한 유보.** Global Data Agreement 는 문언상 **호가·체결 정보(quotation and/or trade information)** 를 대상으로 한다. 우리가 필요한 것은 **애널리스트 추정치 컨센서스**이며, 이것이 같은 계약으로 커버되는지, 별도 상품·별도 공급사(추정치는 대개 제3자 집계사에서 온다)인지 **확인하지 못했다.** `api.nasdaq.com/api/analyst/...` 가 어떤 상품의 웹 표출인지도 공개 문서로 특정하지 못했다.

#### 문의 시 확인할 항목

1. `api.nasdaq.com/api/analyst/{symbol}/earnings-forecast` 가 어떤 정식 상품에 대응하는가. 상품명과 계약 유형.
2. 애널리스트 추정치가 Global Data Agreement 범위인가, 별도 라이선스인가. 원천 집계사가 어디인가.
3. **EPS 정의가 GAAP 인가 조정(비GAAP)인가.** 응답 헤더의 `Consensus EPS*` 별표 각주 원문.
4. **추정 기준 시각.** 응답의 `asOf` 가 null 인데 계약 경로에서는 제공되는가.
5. 허용 용도. 내부 분석 전용인지, **가공 결과를 공개 배포**할 수 있는지(우리 산출물은 HTML 리포트로 배포된다).
6. 요청 한도·갱신 주기·과거 시점 데이터 제공 여부.
7. 12 개 종목·분기 4 개 수준의 소규모 사용에 대한 최소 요금.

**이 일곱을 받기 전에는 채택 판단을 하지 않는다.** 특히 5 번이 우리에게 결정적이다.

### 2.2 yfinance — 상류가 "personal use only" 다

`yfinance` 는 Yahoo 의 비공개 API 를 감싼 서드파티 라이브러리다. 저장소 README 가 스스로 밝히는 내용이다.

> "yfinance is **not** affiliated, endorsed, or vetted by Yahoo, Inc. It's an open-source tool that uses Yahoo's publicly available APIs."
>
> 도구는 "intended for **research and educational purposes**" 이며 "the Yahoo! finance API is intended for **personal use only**."
>
> 라이선스는 Apache Software License. 다만 다운로드한 데이터의 사용 권리는 **Yahoo 의 이용약관을 따르라**고 안내한다.

출처: [yfinance README](https://raw.githubusercontent.com/ranaroussi/yfinance/main/README.md)

**정리하면 라이브러리 라이선스(Apache)와 데이터 이용 권리가 분리돼 있다.** 코드는 자유롭게 써도 데이터는 Yahoo 약관에 매인다. 그리고 상류 API 는 개인 용도로 한정된다.

**우리 상황에 대한 판단.**

- `AGENTS.md` 는 가격 데이터에 yfinance 를 쓰도록 이미 정하고 있다. 기존 관행이며 이번에 뒤집지 않는다.
- 그러나 **컨센서스 수집으로 용도를 넓히는 것은 별개 판단이다.** 우리 산출물은 `output/<slug>.html` 로 **배포되는 리포트**이고, 그 안에 제3자 애널리스트 추정치를 실어 나르게 된다. "personal use only" 와 정면으로 부딪힐 소지가 크다.
- Nasdaq 에서 "무료로 응답한다 ≠ 이용 허가" 를 확인한 직후다. 같은 종류의 판단 오류를 반복하지 않으려면 **확대 전에 Yahoo 약관을 직접 검토해야 한다.**

**권고: 가격 용도는 현행 유지, 컨센서스 용도로 확대하지 않는다.** 확대가 필요하면 Yahoo 약관 검토를 선행 조건으로 둔다.

## 3. 2Q×2 proxy 의 실측 오차

정책 비교의 근거를 말이 아니라 숫자로 만들었다. **과거 실제 분기 실적**으로 proxy 를 백테스트했다. 최근 4 개 분기 실적 합(참값)과 앞 2 개 분기 합×2(proxy)를 비교한다.

원천은 Finnhub `stock/earnings` 의 `actual` 이다. 추정치가 아니라 발표된 실적이므로 **추정 오차가 섞이지 않은 순수한 계절성·추세 오차**다.

### 3.1 밴드 전환 확률

F6 밴드 경계는 20·29·42·62·90 이고 인접 배율이 약 **1.45 배**로 균등하다. EPS 오차 `e` 는 PER 을 `1/(1+e)` 배로 움직인다. 밴드 안에서 PER 이 로그균등이라고 보면 경계를 넘을 확률은 `|ln(1+e)| / ln(1.45)` 다.

| 오차 | PER 변동 | **밴드 전환 확률** |
|---|---|---|
| 중앙값 8.9% | 8.2% | **약 23%** |
| 최대 23.3% | 18.9% | **약 56%** |

**중앙값 수준에서도 네 번에 한 번꼴로 F6 점수가 한 칸 달라진다.** 최대 수준에서는 절반이 넘는다. F6 은 -5~0 의 6 단계뿐이라 한 칸이 곧 총점 1 점이다.

### 3.2 더 나쁜 것 — 편향이 평가 축과 상관된다

오차 부호가 무작위가 아니다.

- **상승 추세 기업은 계통적으로 마이너스**다. NVDA -16.7%, PLTR -23.3%, TSM -14.3%. 뒤 두 분기가 크므로 앞 두 분기를 두 배 해도 못 미친다.
- **하락·정체 기업은 플러스**다. META +8.9%, TSLA +14.9%.

EPS 과소평가는 PER 과대평가이고 곧 **더 나쁜 F6 점수**다. 즉 **고성장 기업이 체계적으로 불리하게 채점된다.** 우리 채점표가 측정하려는 것이 바로 성장·과점 구조인데, proxy 는 그 축과 상관된 편향을 만든다. 무작위 잡음이면 표본이 늘수록 상쇄되지만 이건 상쇄되지 않는다.

### 3.3 실제 오차는 이보다 크다

위 측정은 **발표된 실적**으로 한 것이다. 실전에서는 미래 2 분기의 **추정치**를 쓰므로 추정 오차가 위에 더 얹힌다. SPCX 사례가 그 크기를 보여준다. 같은 2026Q3 컨센서스가 Nasdaq 0.09, Yahoo 0.1458 로 **62% 차이**였다(`../spacex-eps-source-03/REPORT.md` 7.2).

**따라서 8.9%/23.3% 는 오차의 하한이다.**

## 4. 정책안 비교

| 안 | 내용 | 장점 | 단점 | 판정 |
|---|---|---|---|---|
| **A. 현행 유지** | 4Q 미충족 시 `pending_data`. 2Q 는 수집하지 않음 | 규칙 단순, 오염 없음 | 확보한 자료를 버림 | 차선 |
| **B. 2Q 보존 + 점수 없음** | 2Q 를 관측으로 등록하되 F6 는 `pending_data` | 자료 축적, 오염 없음, 4Q 도달 시 즉시 활용 | 당장 순위는 안 열림 | **권고** |
| **C. 2Q×2 를 flag 부 정식 점수** | proxy 로 채점하고 경고 표시 | 순위가 열림 | 3.1~3.3 의 편향이 점수에 들어감. 경고는 점수를 고치지 못함 | **반대** |
| **D. 2Q×2 를 별도 참고 지표** | 점수와 분리해 참고란에만 표기 | 정보 제공 | 화면에 두 개의 PER 이 공존해 오독 위험 | 조건부 |

### 4.1 왜 C 를 반대하는가

"경고를 붙이면 되지 않나" 가 자연스러운 반론이다. 세 가지 이유로 부족하다.

1. **점수는 경고를 반영하지 않는다.** 순위·총점·history.csv 에는 숫자만 남는다. 경고는 화면에만 있고 시계열에는 없다.
2. **편향이 방향성을 가진다**(3.2). 경고는 "부정확할 수 있음" 을 알릴 뿐 "고성장 기업이 불리하게 나온다" 는 계통 편향을 보정하지 못한다.
3. **우리 규칙이 이미 같은 판단을 했다.** `annual_weighted_proxy` 는 `proxy_methods` 로 분리돼 실행 단위 결정(C-13) 없이는 채점에 못 쓴다. 2Q×2 는 그보다 근거가 약한 근사인데 이를 정식 점수로 허용하면 **기존 규칙보다 느슨한 예외**를 새로 만드는 셈이다.

### 4.2 왜 B 인가

공통 방법 문서가 이미 정한 원칙과 맞는다.

> "통계 항목 일부가 없으면 결측으로 기록한다. … 필수 채점 입력의 결측과 보조 정보의 결측을 분리한다."

2 분기 확보는 **필수 입력의 부분 확보**다. 보존하되 점수를 만들지 않는 것이 이 원칙의 직접 적용이다. 그리고 `coverage` 를 명시적으로 기록하면 4 분기 도달 시점을 추적할 수 있다.

## 5. 권고안 상세

### 5.1 관측 등록 형태

2 분기 값을 버리지 않고 다음 형태로 보존한다. **아래는 설계안이며 이번에 구현하지 않았다.**

- 분기별로 개별 관측을 만든다. `metric: ntm_eps_quarter`, `period: "2026Q3"` 처럼 분기를 명시한다.
- `basis` 에 `currency`, `share_basis`, `method`, `vendor`, `estimate_asof` 를 채운다. 미표시면 `null` 이 아니라 **미확인으로 기록**한다.
- 보조통계(`low`, `high`, `n`)는 있으면 넣고 없으면 결측으로 둔다. 없다고 평균을 버리지 않는다.
- **합산은 저장하지 않는다.** 4 분기가 모이면 계산기가 합한다. 부분 합을 미리 만들어 두면 그 값이 NTM 처럼 쓰일 위험이 있다.

### 5.2 F6 상태

```
확보 분기 < 4  →  status = pending_data
                  pending.message = "NTM EPS 4분기 중 N개 확보 — 나머지 (4-N)개 필요"
                  calc.coverage = {"secured": N, "required": 4, "quarters": [...]}
```

`coverage` 를 `calc` 에 남기면 화면에서 2/4·3/4 를 구분해 보여줄 수 있다. **점수는 만들지 않는다.**

### 5.3 4Q 확보 시 전환 규칙

자동 승격을 두지 않는다.

1. 4 개 분기가 모두 같은 공급사에서 모이고
2. 분기가 연속이며 미발표 창과 일치하고(`_quarters_problem` 통과)
3. `currency`·`share_basis` 가 주가와 일치하고(`_basis_alignment` 통과)
4. 각 관측의 `status` 가 `verified` 일 때

에만 `method: consensus_4q_sum` 으로 계산 대상이 된다. 그리고 이는 **입력 변경**이므로 `calculate → draft → review → approve` 를 다시 밟는다. 승인된 실행이 조용히 바뀌지 않는다.

**공급사 혼합 금지를 코드로 강제할 것을 함께 권고한다.** 현재는 문서 규칙이다. 4 개 분기의 `source_id` 가 하나가 아니면 `pending_data` 로 떨어뜨리는 검사가 있으면 좋겠다.

### 5.4 불확실성 표시

점수를 만들지 않으므로 경고가 아니라 **상태 표시**가 된다. 화면에는 확보 분기 수, 원천, 부족 분기, 표본 수 결측 여부를 그대로 보여준다. 이미 「자료 확보 현황」 섹션이 이 역할을 한다.

## 6. C-13 과의 관계

C-13 은 "TSMC·Alibaba 의 연간 EPS 가중 근사를 NTM 으로 쓸 것인가" 이고 선택지가 `accept_proxy_with_flag` / `reject_proxy` 다.

**이번 조사는 `reject_proxy` 쪽 근거를 강화한다.**

- 연간 근사와 2Q×2 근사는 **같은 종류의 오류**를 만든다. 분기 분포를 모른 채 총합을 추정하는 것이다.
- 3.2 의 계통 편향은 연간 근사에도 적용된다. 연간 EPS 를 NTM 으로 쓰면 미발표 4 분기 창과 회계연도 창이 어긋나 성장 기업에서 같은 방향의 편향이 생긴다.
- `accept_proxy_with_flag` 를 택하면 2Q×2 를 거부할 논리적 근거가 약해진다. **두 결정은 같은 원칙 위에 있어야 일관된다.**

다만 **C-13 은 사용자·설계진행의 결정이며 이 보고서가 확정하지 않는다.** 현행 미결 상태를 유지한다.

## 7. 예외 처리

### 7.1 비상장 (OpenAI, Anthropic)

**변경 없음.** 비상장 F6 는 `private_score_mode: manual_with_rationale` 로 정성 예외다(C-12). NTM EPS 요건 자체가 적용되지 않으며 이번 정책안과 무관하다. 2Q proxy 를 비상장에 적용하지 않는다.

### 7.2 TSM · BABA

분기 수보다 **기준 문제가 먼저**다. `../nasdaq-eps-expansion-04/REPORT.md` 7 절에서 확인한 대로 공급사마다 통화·주식 단위가 다르다.

| | SEC(실적) | Finnhub | FMP | Yahoo |
|---|---|---|---|---|
| TSM | TWD·USD 보통주 | TWD 보통주 | TWD ADR | **USD ADR** |
| BABA | CNY·USD 보통주 | CNY ADS | CNY ADS | **CNY ADS** |

우리 F6 은 **USD × ADR/ADS** 기준이 필요하다(미국 상장 주가 기준).

- TSM 은 Yahoo 가 그 조합을 바로 준다.
- **BABA 는 어느 무료 원천도 USD 로 주지 않는다.** CNY 를 환산해야 하고, 그러면 환율 시점이라는 변수가 추가된다.

**권고: 두 종목은 4 분기가 모이더라도 `basis` 검산을 통과하기 전까지 `pending_data` 로 둔다.** 검산 방법은 `순이익 ÷ EPS` 로 함의 주식수를 역산해 보통주·ADR/ADS 중 어느 쪽인지 판정하는 것이다(같은 보고서 7 절).

### 7.3 SPCX

`../spacex-eps-source-03/REPORT.md` 대로 SEC XBRL 이 `USD/shares` 보통주로 basis 를 확정해 준다. 미국 직상장이라 ADR 문제가 없다. **분기 수만 부족하다**(Yahoo 2/4, Finnhub 0/4). 위 5 절 정책이 그대로 적용된다.

## 8. 최종 권고

1. **Nasdaq — 문의하되 채택 보류.** `DataOps@nasdaq.com` 에 2.1 의 일곱 항목을 문의한다. **회신 전까지 추가 호출 금지.** 특히 "가공 결과의 공개 배포 허용 여부" 가 부정이면 우리 용도에 무의미하므로 그것부터 확인한다.
2. **yfinance — 컨센서스 용도로 확대하지 않는다.** 가격 용도는 `AGENTS.md` 대로 유지한다. 확대가 필요하면 Yahoo 약관 검토를 선행 조건으로 둔다.
3. **2Q×2 proxy 를 정식 점수로 허용하지 않는다.** 오차 중앙값 8.9%·최대 23.3%, 밴드 전환 확률 23~56%, 그리고 고성장 기업에 불리한 계통 편향(3.2) 때문이다. 이 편향은 우리 평가 축과 상관되므로 표본을 늘려도 상쇄되지 않는다.
4. **확보한 2 분기는 보존한다**(안 B). 분기별 개별 관측으로 등록하고 `coverage` 를 `calc` 에 남기며 F6 는 `pending_data` 로 둔다.
5. **4Q 확보 시 자동 승격을 두지 않는다.** 5.3 의 네 조건을 모두 만족할 때만 `consensus_4q_sum` 이 되고, 입력 변경이므로 재계산·재리뷰·재승인을 거친다.
6. **공급사 혼합 금지를 코드로 강제할 것을 제안한다.** 현재는 문서 규칙뿐이다.
7. **C-13 은 미결 유지.** 다만 `reject_proxy` 와 위 3 번이 같은 원칙 위에 있음을 기록한다. 두 결정을 따로 내리면 규칙이 어긋난다.
8. **TSM·BABA 는 분기 수와 무관하게 basis 검산을 선행 조건으로 둔다.** BABA 는 USD 원천이 없어 환산 시점 문제가 추가된다.

**이 권고는 구현이 아니다.** 어느 것도 코드·규칙·점수에 반영하지 않았다. 채택 여부는 사용자·설계진행 결정이다.

## 9. 미확인 사항

1. **Nasdaq 애널리스트 추정치의 상품 구분과 라이선스 범위.** 2.1 의 일곱 항목 전부. 문의하지 않았다.
2. **Nasdaq 추정치의 원천 집계사.** 대개 제3자인데 특정하지 못했다.
3. **Yahoo 이용약관 원문 검토.** yfinance README 의 인용만 확인했고 Yahoo 약관 본문을 읽지 않았다.
4. **밴드 전환 확률의 분포 가정.** 3.1 은 밴드 내 PER 이 로그균등이라는 가정 위의 추정이다. 실제 12 개사 PER 분포로 다시 계산하면 값이 달라질 수 있다.
5. **추정 오차의 크기.** 3.3 에서 실제 오차가 하한보다 크다고만 했고 정량화하지 못했다. 과거 컨센서스와 실적을 짝지어 측정할 수 있으나 이번에 하지 않았다.
6. **Finnhub `stock/earnings` 의 과거 분기 수집 범위.** 티커당 4 개 분기만 확보돼 표본이 얕다. 더 긴 이력으로 백테스트하면 오차 추정이 안정된다.
7. **유료 경로 비용.** Finnhub `stock/eps-estimate` 와 FMP 유료 분기의 실제 요금과 4 분기·표본 수 제공 여부.
